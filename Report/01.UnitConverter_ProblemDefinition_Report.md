## 1. 요약

UnitConverter_10은 길이 단위(meter, feet, yard) 변환 CLI 프로그램 실습 프로젝트이다.  
본 보고서는 **솔루션 착수 전** Mom Test 인터뷰·시뮬레이션을 통해 **진짜 문제**를 정의하고, README 요구사항·ECB 설계·테스트 전략과 연결한다.

**핵심 결론 (한 문장):**

> 단위가 섞인 값을 다룰 때 **관계·방향·숫자를 바로 판정하지 못해** 외부 탐색·재확인·작업 중단 비용이 발생하며, 이를 **단일 출처의 변환 규칙 + 자동 검증**으로 줄이는 것이 본 프로젝트의 문제 정의이다.

## 2. 페르소나

### 2.1 페르소나 A — 실습 학습자 (실제 인터뷰)

| 항목 | 내용 |
|------|------|
| **역할** | UnitConverter를 손으로/코드로 다루는 **프로그래밍 학습자** |
| **상황** | 미국·한국 단위 차이로 영어 문서(feet, yard) 확인 시 meter 감각으로 판단 어려움 |
| **현재 대안** | 인터넷 단위 변환기 검색, UI가 직관적인 사이트 선별 |

### 2.2 페르소나 B — 수업 과제 학생 (⚠️ 가상 시뮬레이션)

| 항목 | 내용 |
|------|------|
| **역할** | 프로그래밍 수업에서 **Unit Converter 과제**를 받은 학생 |
| **상황** | 과제 PDF·검색·암산만으로 단위 관계·곱/나눗셈 방향 판정 지연 |
| **현재 대안** | PDF 재탐색, 블로그/위키 비교, 계산기 양방향 재확인 후 코딩 |

> **주의:** 페르소나 B는 교육용 **합성 인터뷰**이며, 페르소나 A의 실제 경험과 **혼합하지 않음**.

## 3. Mom Test 인터뷰 결과

### 3.1 페르소나 A — 인터뷰 요약

| 항목 | 과거 사실 (증거) |
|------|------------------|
| 막혔을 때 행동 | 인터넷에서 단위 변환기 검색 후 변환 |
| 소요 시간 | **약 10분 이상** |
| 탐색 비용 | **4~5개** 사이트 열람 |
| 포기 사유 | 영어·복잡 UI, 카테고리 **한 단계 더** 선택하는 UI |
| 포기 후 행동 | 다른 사이트 찾으러 이탈 |

**Mom Test 증거 3줄 (인용):**

1. "막혔던 순간에 **인터넷에서 단위 변환기를 검색**해서 변환을 했었어."
2. "**대략 10분 이상**이 걸렸던거 같아."
3. "**4~5개는 열어본거 같아.** 우선 UI가 깔끔하고 복잡하지 않고 직관적인 사이트를 찾아봤었어."

### 3.2 페르소나 B — 시뮬레이션 요약 (⚠️ 가상)

| 항목 | 과거 사실 (합성) |
|------|------------------|
| PDF 공백 | yard 환산표 없음 → PDF만 **다시 넘김** |
| 외부 자료 상충 | 블로그·위키 **소수 자리 불일치** → **약 5분** 비교 |
| 방향 혼동 | 3.28084 **곱/나눗** 헷갈림 → 계산기 **양방향 2회**, **약 3분** 후 코딩 |

**진짜 문제 (한 문장):**

> 과제 예시만으로는 단위 관계·곱셈/나눗셈 방향을 바로 판정하지 못해, 외부 자료 검색·상충하는 숫자 비교·양방향 재확인에 시간을 쓴 뒤에야 코딩을 시작할 수 있다.

## 4. 표면 문제 vs 진짜 문제

### 4.1 표면 문제 (❌ 하지 않을 정의)

| 표면 문제 | 왜 잘못됐는가 |
|-----------|---------------|
| ~~"feet·yard를 meter로 **자동 변환해 주는 프로그램**을 만든다"~~ | 솔루션(프로그램·자동 변환)이 문제에 섞임 |
| ~~"**웹 단위 변환기 UI**를 대체한다"~~ | Mom Test 진짜 문제는 UI 부재가 아니라 **판정·탐색·재확인 비용** |
| ~~"**TDD/PyQt/Cursor**로 개발한다"~~ | 도구명은 문제 정의가 아님 |

### 4.2 진짜 문제 (✅ 채택)

| 관점 | 진짜 문제 (한 문장) |
|------|---------------------|
| **페르소나 A** | 영어 문서를 읽다가 feet·yard를 meter 감각으로 바로 판정하지 못할 때, **읽기가 중단**되고 변환기 탐색·선별에 **10분+·4~5개 사이트**를 쓴다. |
| **페르소나 B** | 과제 PDF·검색만으로는 **단위 관계·곱/나눗셈 방향**을 확정하지 못해, **외부 비교·양방향 재확인** 후에야 코딩을 시작한다. |
| **통합** | **단위 관계·변환 방향·수치 신뢰**를 즉시 판정하지 못해 **작업 흐름이 끊기고** 재탐색·재확인 **시간 비용**이 발생한다. |

## 5. 문제 → 설계 연결 (ECB)

Mom Test에서 드러난 **판정 지연**을 ECB 역할 분리로 해결한다.

| ECB | 역할 | Mom Test 연결 |
|-----|------|---------------|
| **Entity** | `LengthInput`, `LengthInMeters`, `ConversionResult`, `UnitRatio` | README **단일 상수** (3.28084, 1.09361) |
| **Control** | `InputValidator`, `Solver` | 곱/나눗 방향·yard 누락 → **Solver + 테스트**로 고정 |
| **Boundary** | `InputHandler`, `ResultDisplay` | 웹 UI 탐색 대신 **`unit:value` CLI** 로 입력 단순화 |

**데이터 흐름:**

```
InputHandler → InputValidator → Solver(+UnitRatio) → ConversionResult → ResultDisplay
```

## 6. 세션 3 — Test Loop (Mom Test 검증 전략)

### 6.1 주제 (솔루션 최소화)

과제 PDF·검색·암산만으로는 단위 관계와 곱/나눗셈 방향을 바로 판정하기 어렵기 때문에, meter·feet·yard 변환을 **테스트로 고정**해 코딩 전·중 **재확인 시간**을 줄인다.

### 6.2 R-G-I-O

| 항목 | 내용 |
|------|------|
| **Role** | Unit Converter 과제 수행 학습자 |
| **Goal** | PDF·블로그·계산기 재확인 없이 README 비율로 **변환 판정** |
| **Input** | `unit:value` + README 상수 |
| **Output** | 통과하는 pytest + 실패 시 **단위·방향** 노출 |

### 6.3 성공 기준 (Mom Test 증거 연결)

| # | 기준 | 증거 연결 |
|---|------|-----------|
| S1 | meter·feet·yard 테스트 + README 기대값 명시 | yard PDF 공백 |
| S2 | README 고정 상수만 사용, meter 기준 정규화 검증 | 블로그/위키 5분 상충 |
| S3 | 곱/나눗 오류 시 즉시 FAIL, `pytest` 1회 재확인 | 계산기 양방향 3분 |

### 6.4 현재 구현 상태

- `tests/test_converter.py`: 변환 3건 + 입력 검증 3건 (**6 passed**)
- 상수: `METER_TO_FEET = 3.28084`, `METER_TO_YARD = 1.09361`
